# Manuscript-ready methodology and results

## Methodology

Non-functional testing was conducted using the UniPM source and test commits identified in the evidence records. Android 10/API 29 (Nexus 5, 360×640 dp) and Android 14/API 34 (Pixel 7 Pro, approximately 411×891 dp) were exercised through GitHub Actions on Ubuntu 24.04 with Flutter 3.47.1, Java 21, x86_64 emulators, and software rendering. Each job built and installed a debug APK, attempted to launch `MainActivity`, captured a startup screenshot, and ran four app-configuration tests. The application source at the Android run was `530b5be36727698f3e66935e56e53c698e4df52b`. A separate local Android 17/API 37 smoke used an isolated SQL Server database containing synthetic records and a synthetic development account. Web performance testing used the local ASP.NET Core API and synthetic data: five warm-up requests followed by 30 sequential measurements for each of three authenticated registry endpoints; timing ended after the complete response body was read and did not include React rendering. OWASP ZAP 2.17.0 spidered the loopback API and performed passive analysis before and after a response-header correction; no active scanner or authenticated session was used.

## Results

Both required Android CI jobs completed with a successful workflow conclusion. On each configuration, the debug APK built and installed, `MainActivity` was reported, the app process was present, and the four app-configuration tests passed. However, `am start -W` returned a timeout and the captured API 29 and API 34 screenshots showed Android “System UI isn't responding” and “Pixel Launcher isn't responding” dialogs, respectively, over blank screens. As the UniPM interface was not visible, login, authenticated navigation, responsive content, asset lookup, inspection forms, offline draft persistence, synchronization, maintenance history, and live error/conflict handling were not verified on either required profile. The supplemental API 37 smoke successfully completed synthetic-account login/navigation, asset search/details, and display of two acknowledged maintenance-history entries; its PM form list timed out, and live offline synchronization and conflict recovery were not executed. The existing Flutter suite passed 198 tests on API 37; its draft, history, offline, and error cases use fakes/test doubles.

Across 90 measured API requests, every request returned HTTP 200. Asset registry latency was median 11.477 ms, p95 25.715 ms, and maximum 40.062 ms; preventive-maintenance schedule registry latency was 14.257 ms, 20.265 ms, and 30.365 ms; inspection registry/form-review latency was 19.063 ms, 24.176 ms, and 87.070 ms, respectively. The React test suite passed 278 tests across 32 files, and its production build/typecheck passed. The initial passive ZAP report contained one low-risk missing `X-Content-Type-Options` header alert and two informational alert types. After `X-Content-Type-Options: nosniff` was added and the focused header regression passed, a repeated passive report did not contain the header alert; the same informational alert types remained. The initial npm audit recorded 43 affected package entries (13 high and 30 moderate); source-lockfile comparison classified 3 as runtime/transitive and 40 as development. After compatible dependency updates, the full audit recorded 10 moderate development-only entries and no high or critical findings, while the production-only audit reported zero.

## Limitations

The Android Actions conclusion covers APK build/install/process checks and four API-configuration tests, not application workflow acceptance; the actual screenshots document the startup-rendering failure. API 29 and API 34 authenticated and offline workflows remain untested, and the API 37 smoke is supplemental only. The API benchmark is a single-user, serial development measurement with warmed application/database paths, not a capacity or service-level test. The ZAP exercise is unauthenticated and passive and does not cover active attacks, authenticated authorization, deployed infrastructure, or all security properties. These results are bounded development evidence and should not be presented as complete Android compatibility, production performance, or complete security validation.
