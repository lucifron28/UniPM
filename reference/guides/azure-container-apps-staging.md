# Azure Container Apps staging preparation

This guide prepares a Linux container for the existing published .NET 10 API and bundled React web app. It does not create or deploy Azure resources. No migrations, seed operations, reset commands, or live SQL calls belong in this workflow. The existing Azure SQL database already contains user data; treat it as live.

## Local package and context

The image wraps the existing combined App Service publish ZIP. It does not rebuild the frontend or backend from source. The preparation script checks that the working tree is clean, the current commit matches `provenance.json`, the ZIP SHA-256 matches both provenance and its sidecar, and the archive contains the required API/runtime/frontend files. It extracts only validated archive paths into a new ignored directory and writes `publish-manifest.json` with each extracted file's length and SHA-256. It rejects environment files, environment-specific appsettings files, credential/key files, source maps, PDBs, and populated credential-like values in `appsettings.json`. It never overwrites or removes an existing context.

Run this command only after the preparation patch has been reviewed and committed, then a fresh package has been created for that exact commit on `deploy/azure-staging`:

```powershell
pwsh -NoLogo -NoProfile -File scripts/prepare-container-apps-context.ps1
```

The current base package is tied to `1c828bba28eb8b88496691bd48385609126d012e`; it cannot be reused after these files change HEAD. The context path is `artifacts/container-apps-context/<commit-sha>` and is ignored by Git. Docker is installed locally, but the Docker Desktop Linux engine was unavailable during preparation, so no image build has been verified.

The Dockerfile uses the official .NET 10 ASP.NET runtime image, binds Kestrel to port 8080, and runs as the image's non-root `APP_UID`. The Docker context contains the Dockerfile, `.dockerignore`, extracted `app/`, and a local manifest; the manifest is excluded from the image context. [Microsoft .NET container images](https://learn.microsoft.com/en-us/dotnet/core/docker/container-images)

## Proposed cost-limited configuration

Use one Azure Container Apps environment in Japan East and one Consumption workload profile app. Set the container to 0.25 vCPU and 0.5 GiB, minimum replicas 0, maximum replicas 1, HTTP ingress target port 8080, and the worker option off. Scale-to-zero means the app may cold-start after idle periods. This is for a restricted staging demonstration, not continuous availability.

The Consumption grant provides 180,000 vCPU-seconds, 360,000 GiB-seconds, and 2 million HTTP requests per subscription each calendar month. At 0.25 vCPU and 0.5 GiB, the CPU and memory grants each cover 720,000 active seconds, or 200 hours, if no other Container Apps workloads consume them. The free grant is not an account-specific budget guarantee. Excess compute/requests, outbound data, registry storage or transfer, and any selected monitoring service can add charges. Set the environment log destination to `none` for the initial cost-controlled run if the operator accepts that logs will not be retained; real-time log streaming remains available. Do not create a Log Analytics workspace for this plan. [Consumption billing](https://learn.microsoft.com/en-us/azure/container-apps/billing) · [Logging destinations](https://learn.microsoft.com/en-us/azure/container-apps/log-options) · [Replica scaling](https://learn.microsoft.com/en-us/azure/container-apps/scale-app?pivots=azure-cli)

The read-only Azure discovery reported the Container Apps provider as `Registered` and app quota of 1 in each of four inspected regions. This does not verify regional compute allocation or guarantee a successful start. No new VNet, NAT gateway, private endpoint, dedicated workload profile, or Azure Container Registry is included. Select an already approved OCI registry before any later push; registry creation and image publication need separate approval.

## Data access and safety gates

Explicitly set `PreventiveMaintenanceScheduleGeneration__WorkerEnabled=false`; the worker defaults to enabled if omitted. With migrations and seeding disabled, use a dedicated least-privilege runtime SQL identity, not an administrator identity; it needs only `db_datareader` and `db_datawriter` for the existing application workflows. Do not grant DDL, `db_owner`, or migration permissions. Its connection string has not been provisioned or verified; supply it only through the operator's secure Container Apps configuration process. Never put it in a command argument, image, context file, or log.

Enable a Container Apps managed identity for the app. The code's Blob provider uses `DefaultAzureCredential` and the existing private `inspection-photos` container. Assign `Storage Blob Data Contributor` at that container scope only, after approval. Configure the existing Blob service URI and `InspectionPhotoEvidence:StorageProvider=AzureBlob` through the service configuration. Confirm the storage account's network rules allow the app's path before enabling photo operations; identity permission does not bypass storage network restrictions. Do not switch to the local filesystem provider because container storage is ephemeral. [Managed identities](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity) · [Container-scoped Blob role](https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access)

Before any tester access, record the exact outbound IPs reported for the chosen Container Apps environment and confirm the egress behavior can be allowlisted narrowly at Azure SQL. Add only those exact addresses after owner approval. Do not enable the broad `0.0.0.0` “Allow Azure services” firewall rule, a regional IP range, or a wide port range as a workaround. Verify the SQL connection policy and required outbound ports; if the required source IPs or ports cannot be kept narrow, stop and use an approved network design. SQL connectivity and database permissions remain untested. [Azure SQL network controls](https://learn.microsoft.com/en-us/azure/azure-sql/database/network-access-controls-overview?view=azuresql) · [SQL connection policy and ports](https://learn.microsoft.com/en-us/azure/sql-database/sql-database-troubleshoot-common-connection-issues)

Before any tester access, set `ASPNETCORE_ENVIRONMENT=Production`, `ASPNETCORE_HTTP_PORTS=8080`, `AllowedHosts` to the verified Container Apps hostname, and `UNIPM_WEB_ORIGIN` to its exact HTTPS origin. Set `UNIPM_JWT_ISSUER`, `UNIPM_JWT_AUDIENCE`, and `UNIPM_JWT_SIGNING_KEY` consistently with the client; the signing key must contain at least 32 bytes. Explicitly set `Embeddings__Enabled=false`, `NaturalLanguageAnalytics__Enabled=false`, and `Observability__MetricsEnabled=false` for the PMIS validation host. Validate login, refresh, and logout with the secure refresh cookie before inviting the four existing testers. Inject secrets only through an approved secure operator process. Do not use plaintext command-line values or files. No Azure resources, role assignments, firewall rules, registry, or app settings have been changed.
